# Docksmith — MVP 개발 로드맵 (1인 개발자 기준)

**전제**: 혼자 개발한다. 시간 추정은 "하루를 집중해서 개발에만 쓸 수 있는 날" 기준의 작업일(man-day)이다. 본업(물류 실무)과 병행한다면 실제 캘린더 기간은 2~3배로 늘어난다고 보면 된다.

**대원칙**: 한 번에 다 만들지 않는다. **MVP → Beta → V1 → V2 → Enterprise** 순서로 가고, 각 단계는 "이전 단계가 검증되어야 다음이 의미 있다"는 전제로 짜여 있다. 특히 MVP는 결제 기능도 없이 "이걸 남에게 써보라고 줬을 때 실제로 시간을 아껴주는가"만 증명하는 데 집중한다.

---

## 요약 (전체 그림)

| 단계 | 목표 한 줄 | 예상 작업일 | 완료 시 할 수 있는 것 |
|---|---|---|---|
| MVP | 핵심 가치(클릭 매핑 + 대량 생성) 증명 | 약 25~30일 | 무료로 실제 사용자에게 써보라고 줄 수 있음 |
| Beta | 돈을 받을 수 있게 만들고 첫 유료고객 확보 | 약 15~18일 | Stripe로 결제, SEO 페이지로 유입, 사용량 제한 |
| V1 | 이탈률을 낮추는 "정착" 기능 | 약 20~25일 | 팀 사용, Shopify 연동, 재방문 강화 |
| V2 | 물류를 넘어 플랫폼으로 확장 | 약 30~35일 | Word/Excel, API 공개, AI 보조 |
| Enterprise | 특정 대형 고객 요구에 맞춤 대응 | 고객 요청 발생 시 그때그때 | SSO, 화이트레이블, SLA |

## PHASE 1 — MVP (핵심 가치 증명)

> 목표: "PDF 업로드 → 필드 클릭 → CSV 업로드 → ZIP 다운로드"가 실제로 작동하고, 내가 직접 실무에서 써도 시간이 줄어드는지 확인한다. 결제, 팀 기능, SEO는 여기서 제외.

### 1.1 프로젝트 뼈대 세팅
- **목표**: Next.js + TypeScript + Tailwind + Prisma + Docker + Supabase 프로젝트 초기 세팅, GitHub Actions CI 스켈레톤
- **예상 작업일**: 2일
- **난이도**: 하
- **왜 필요한가**: 이후 모든 기능이 이 뼈대 위에서 만들어진다. 여기서 대충 하면 나중에 구조를 갈아엎게 된다(ARCHITECTURE.md에서 미리 정한 스택을 그대로 적용).
- **다음 단계 연관성**: 인증/DB 스키마 작업의 전제 조건.

### 1.2 인증 (로그인/가입)
- **목표**: Supabase Auth로 이메일 가입 + Google OAuth, 로그인 시 org 자동 생성(1계정=1org)
- **예상 작업일**: 2일
- **난이도**: 하 (Supabase Auth SDK가 대부분 처리)
- **왜 필요한가**: 템플릿/데이터가 "누구 것"인지 구분되어야 그 다음 어떤 기능도 만들 수 없다.
- **다음 단계 연관성**: 템플릿 업로드는 반드시 로그인된 org에 귀속된다.

### 1.3 템플릿 업로드
- **목표**: PDF 업로드 → Supabase Storage 저장 → `templates` 테이블에 메타데이터 기록
- **예상 작업일**: 2일
- **난이도**: 하
- **왜 필요한가**: 매핑 스튜디오가 렌더링할 대상이 있어야 한다.
- **다음 단계 연관성**: 다음 단계(1.4)가 이 파일을 화면에 그린다.

### 1.4 PDF 렌더링 + 필드 클릭 매핑 UI ★ 이 프로젝트에서 가장 핵심이자 가장 어려운 부분
- **목표**: `pdfjs-dist`로 PDF를 캔버스에 그리고, 사용자가 클릭/드래그로 사각형을 지정하면 그 좌표를 필드로 저장. 필드 속성 패널(이름/타입) 포함.
- **예상 작업일**: 6~8일
- **난이도**: 상 (좌표계 변환, 줌/스크롤 시 오버레이 위치 동기화, 여러 페이지 처리가 까다롭다)
- **왜 필요한가**: 이게 이 제품의 존재 이유다. 여기가 어설프면 전체 제품이 의미 없다. 경쟁사 대비 차별점("클릭 몇 번으로 매핑")이 이 화면 하나의 완성도에 달려 있다.
- **다음 단계 연관성**: 저장된 필드 좌표가 1.6(생성 엔진)에서 그대로 쓰인다.

### 1.5 CSV 업로드 + 컬럼-필드 매칭
- **목표**: `papaparse`로 CSV 파싱, 컬럼명을 딕셔너리 기반으로 필드에 자동 매칭(예: "Invoice No" ↔ `invoice_no`), 매칭 실패 컬럼은 수동 드롭다운으로 연결
- **예상 작업일**: 3일
- **난이도**: 중
- **왜 필요한가**: 사용자가 매번 컬럼을 손으로 다 맞추면 "자동화"라는 가치가 사라진다. 딕셔너리 매칭이 초반 마법 같은 경험(aha moment)을 만든다.
- **다음 단계 연관성**: 매칭이 끝난 데이터가 1.6으로 그대로 전달된다.

### 1.6 클라이언트 사이드 대량 생성 엔진
- **목표**: `pdf-lib`로 각 CSV 행마다 필드 좌표에 값을 채운 PDF 생성, Web Worker로 배치 처리(예: 100건씩) + 진행률 표시, `jszip`으로 압축 후 다운로드
- **예상 작업일**: 5일
- **난이도**: 상 (Web Worker와 메인 스레드 간 통신, 대량 처리 시 메모리 관리, 실패 항목 처리)
- **왜 필요한가**: ARCHITECTURE.md에서 정한 "서버 비용 최소화" 원칙의 실제 구현체. 여기서 서버로 새면 이후 전체 비용 구조가 무너진다.
- **다음 단계 연관성**: 여기서 나온 생성 결과 로그(성공/실패 건수)가 대시보드에 표시된다.

### 1.7 대시보드 (템플릿 목록 + 생성 이력)
- **목표**: 내 템플릿 카드 목록, 최근 생성 job 목록(건수/시각)
- **예상 작업일**: 2일
- **난이도**: 하
- **왜 필요한가**: 재방문했을 때 "다시 시작하는 화면"이 없으면 재사용 플로우(PRD 3.2)가 끊긴다.
- **다음 단계 연관성**: Beta 단계의 사용량 제한 UI가 이 화면에 얹힌다.

### 1.8 최소 랜딩페이지 1개 + 배포
- **목표**: 물류 문서 하나("Commercial Invoice Generator")를 타겟으로 한 랜딩페이지 1개, Fly.io에 Docker로 배포
- **예상 작업일**: 3일
- **난이도**: 중 (SEO 페이지는 Beta에서 확장하지만, 배포 파이프라인 자체는 여기서 완성해야 함)
- **왜 필요한가**: MVP를 "나만 쓰는 것"에서 "남에게 링크로 줄 수 있는 것"으로 만든다.
- **다음 단계 연관성**: Beta의 SEO 페이지 대량 생성은 이 페이지 템플릿을 복제/확장하는 작업이다.

**MVP 종료 기준(Definition of Done)**: 실제 물류 실무자(본인 포함) 3~5명에게 링크를 주고, "직접 하던 반복작업 하나를 이걸로 대신 처리했다"는 피드백을 받는다. 여기서 검증 안 되면 Beta로 넘어가지 않는다.

## PHASE 2 — Beta (돈을 받을 수 있게)

> 목표: 사용량 제한 + Stripe 결제 + SEO 페이지 확장으로 "무료 체험 → 유료 전환"이 가능한 구조를 만든다.

### 2.1 사용량 제한 (Free tier 카운터)
- **목표**: 월 20건 생성 제한, 초과 시 업그레이드 유도 모달
- **예상 작업일**: 2일 / **난이도**: 하
- **왜**: 돈을 받기 전에 "왜 돈을 내야 하는지"의 경계선이 있어야 한다.
- **연관성**: Stripe 연동 후 플랜별 한도로 확장된다.

### 2.2 Stripe 결제 연동
- **목표**: Starter/Pro 플랜 Checkout, Webhook으로 구독 상태 동기화, Customer Portal 연결
- **예상 작업일**: 4일 / **난이도**: 중
- **왜**: 매출이 발생하는 지점. ARCHITECTURE.md에서 정한 대로 카드 정보는 우리 서버를 거치지 않는다.
- **연관성**: 이후 모든 유료 기능(팀, Shopify 등)이 이 결제 인프라 위에 얹힌다.

### 2.3 SEO 랜딩페이지 5~10개 확장
- **목표**: Packing List, FedEx Invoice, DHL Invoice, TSCA, MSDS 등 검색어별 페이지 추가
- **예상 작업일**: 4일 / **난이도**: 하
- **왜**: ChatGPT 분석에서 강조한 "범용 문서 자동화"가 아니라 "구체적 검색어" 전략의 실행부.
- **연관성**: 마케팅 채널(유튜브/Reddit)에서 이 페이지들로 트래픽을 보낸다.

### 2.4 온보딩 다듬기 (샘플 템플릿/예시 CSV)
- **목표**: 처음 온 사용자가 자기 파일 없이도 샘플로 3초 안에 결과를 볼 수 있게
- **예상 작업일**: 2일 / **난이도**: 하
- **왜**: Aha moment까지 걸리는 시간이 전환율을 좌우한다.
- **연관성**: SEO 페이지 유입자의 전환율에 직결.

### 2.5 에러 처리/검증 폴리싱 + 모니터링
- **목표**: 행 단위 오류(필수값 누락 등) 명확히 표시, Sentry/PostHog 연동
- **예상 작업일**: 3일 / **난이도**: 중
- **왜**: 유료 고객이 생기는 순간부터 "왜 안 되냐"는 문의 비용이 커진다. 미리 줄인다.
- **연관성**: 이후 모든 단계의 안정성 기반.

### 2.6 프로덕션 인프라 정비
- **목표**: 커스텀 도메인, 백업 정책, 시크릿 관리 정리
- **예상 작업일**: 2일 / **난이도**: 하
- **연관성**: V1의 Shopify Webhook 등 외부 연동이 안정적인 인프라 위에서 돌아가야 함.

## PHASE 3 — V1 (정착시켜서 이탈 막기)

> 목표: 템플릿을 많이 등록한 회사가 다른 서비스로 못 옮기게(전환비용) 만들고, 데이터 입력 방식을 CSV 외로 넓힌다.

1. **템플릿 버전 관리** — 5일 / 중 — 실수로 매핑을 수정해도 이전 버전 복구 가능해야 실무에서 믿고 씀
2. **팀/역할 권한 (Owner/Admin/Member)** — 5일 / 중 — Team 플랜($79)의 실질적 가치. 여러 명이 같은 템플릿 공유
3. **Shopify App (OAuth + 주문 연동 + 서버사이드 생성 Worker)** — 10일 / 상 — Queue/Worker(BullMQ+Redis)를 이 시점에 처음 도입(ARCHITECTURE.md 8장). 무인 자동화라 서버사이드가 필요한 유일한 케이스
4. **클라우드 저장 연동(Drive/Dropbox, 유료 옵션)** — 4일 / 중 — 생성 결과를 서버에 안 두는 원칙을 지키면서도 저장을 원하는 고객을 위한 옵션

## PHASE 5 — Enterprise (고객 요청 기반, 상시)

정해진 순서가 아니라 실제 대형 고객이 요구할 때 그 요구에 맞춰 우선순위를 정한다.

- SSO/SAML, Audit Log, 화이트레이블/커스텀 도메인, 전담 지원 SLA, 우선순위 처리 Queue

---

## 왜 이 순서인가 (요약)

- **MVP에 결제가 없는 이유**: 핵심 가치가 검증되기 전에 결제 로직에 시간을 쓰는 건 낭비다. "돈을 낼 만한가"보다 먼저 "시간을 아껴주는가"를 확인한다.
- **1.4(매핑 UI)와 1.6(생성 엔진)이 MVP 전체 작업일의 절반 이상인 이유**: 이 둘이 제품의 실제 차별점이다. 나머지(로그인, 대시보드, 랜딩페이지)는 있으면 좋지만 베낄 수 있는 부분이고, 매핑+생성 경험의 완성도가 진짜 해자(moat)다.
- **Queue/Worker를 V1까지 미루는 이유**: MVP~Beta 단계에는 "사람이 브라우저 앞에서 클릭"하는 케이스만 있어서 서버가 대신 생성해줄 필요가 없다. Shopify 연동(무인 자동화)이 생기는 순간에만 필요해지므로, 그 전에 만들면 미리 만든 인프라가 놀게 된다.
- **AI를 V2까지 미루는 이유**: PRD에서 정한 "AI 비용은 반복 호출이 아니라 1회성 호출에만 쓴다"는 원칙이 실제로 작동하는지는, 딕셔너리 매칭만으로 얼마나 커버되는지를 먼저 실측해야 판단할 수 있다. 그 데이터가 쌓이기 전에 AI를 넣는 건 원가 구조를 검증 없이 늘리는 것이다.
